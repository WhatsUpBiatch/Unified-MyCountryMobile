A new customer cannot get a working account

LiveSigning up does not create the customer's database

Each customer gets their own database — that is where their people, call history, contacts, menus and departments live. Signing up creates the company record and the admin user, and stops. The database is only created later, as a side effect of the buy a phone number flow.

So if number-buying fails, the customer is left with an account that errors on every screen. That is exactly what happened twice today.

Twelve calls that never hung up

The switch reports six calls in progress. They are not in progress. They are corpses — the oldest has been sitting there since 11:30 yesterday morning.

LiveWhen the browser's audio fails, the call hangs open forever

Each of these calls answered normally, then the browser's audio path failed to establish. FreeSWITCH kept trying to reach the browser, got nothing back, and — because no audio timeout is configured at all — simply held the call open. It will hold it forever.

Every one of these also holds a leg open to your paid outbound carrier, in ringing state, for the same 26 hours.

LiveThese calls produce no record, so they can never be billed or seen

A call record is only written when a call ends. These have not ended. So they do not appear in the customer's call history, do not appear in any report, and — even once pricing is fixed — can never be charged for.

grep for the 26-hour call's id across /opt/call-recordings/cdr/ → no CDR file exists

Root cause foundThis is why the recording uploader has failed 4,303 times

In the first report I flagged four recordings stranded on disk and an upload job failing every minute. Here is why: those four files belong to four of these stuck calls. The uploader looks up which customer a recording belongs to by reading the call record. There is no call record, because the call never ended. So it skips, retries a minute later, and skips again.

Fix the hanging calls and this fixes itself.

Listen, Whisper and Barge dial your carrier

Proven liveFour supervisor buttons place a billable outbound call instead

On Monitoring → All Calls, Monitoring → All Users, Monitoring → Departments and the Live Dashboard there are four buttons: Listen, Whisper, Barge, Intercept. They are also sold on your pricing page — "advanced call monitoring including whisper, barge, and monitor".

No IVR menu has ever played

BlockerThe switch has executed zero IVR menus, ever

"Press 1 for sales" is a headline feature. Customers have built menus — one tenant has two. The switch's log contains not a single IVR execution across its whole history.

When I asked the configuration service to build a real customer's menu, it produced a valid menu that points at audio which does not exist anywhere on the machine:

A caller reaching this menu hears silence, presses nothing useful, and the call times out.

Fix soonAnd the menu's own options point at a route type that does not exist

In the live menu I pulled, pressing 1 transfers the caller to a message destination. That is one of the five forwarding types the call router has no code for — flagged in the first report. So even with audio fixed, option 1 goes nowhere.

Queues

Every queue rings randomly, whatever the admin chose

Proven liveThe queue script overwrites the admin's ring strategy with "random"

The lookup service does the right thing: ask it about a real queue and it returns that queue's actual strategy. But the queue script always sends its own value first, and its own value defaults to random because nothing sets it. The admin's choice is overwritten on every call.

Same service, same queue, one query with the override and one without:

Without override → "strategy": "ring-all", "rings_together": true ← what the admin chose With override → "strategy": "random", "rings_together": false ← what actually happens callcenter-queue.lua line 48: local ring_strategy = session:getVariable("cc_ring_strategy") or "random" The dialplan deliberately does not set cc_ring_strategy — so it is always "random".

The fix is one line: do not send the strategy when it was never set.

Fix soonNo queue has ever been pushed to the switch, and most agents are signed out

All sixteen queues are flagged as never configured. Of thirty-seven agents, twenty-eight are logged out — so a caller reaching most queues gets "nobody can take it right now".

queues with config_applied = false: 16 of 16 agent status: Logged Out 28, On Break 7, Available 2 live queue lookup reply: "Nobody can take it right now - 1 signed out."

Eight more worth knowing

BlockerSecurity alerts are generated and never delivered

The security service raises alerts — too many payment attempts, suspicious activity — and posts them to a notification endpoint that does not exist. Twenty-eight have failed. Nobody has been told about any of them.

security-api error log: Cannot POST /internal/notifications/security-alert ×28 "1 of 1 operator notifications failed"

BlockerPermissions are decoration — the server never checks them

Roles and permissions are configured in detail and enforced entirely in the browser. Not one controller in the API checks a permission before doing what it was asked. Anyone who can log in can call any endpoint directly, whatever their role says.

Eighteen active users additionally carry a role that is a raw id or free text ("New role", "Custom Subadmin"), which no server-side check can match at all.

Fix soonNot one but four single-threaded services sit on the call path

The first report flagged the call router. There are three more beside it — the phone directory, the switch configuration, and the queue agent lookup. All four are one-request-at-a-time Python servers with a five-deep waiting queue. Every call touches at least three of them.

Fix soonThree switch modules fail to load on every start

Including the standard call-record module and the audio-streaming module used for live transcription. They fail on a missing system library.

mod_format_cdr.so, mod_audio_stream.so → cannot open shared object file libevent-2.1.so.7, libevent_core-2.1.so.7 → cannot open shared object file

Fix soonAudio has no fallback when a customer's network blocks it

The media relay is configured with TCP relaying switched off. A customer on a corporate network that blocks the usual audio traffic has no second route — the call connects and stays silent, which is how these stuck calls start.

/etc/turnserver.conf: no-tcp-relay Secure relay offered on port 5349 only — commonly blocked; port 443 is not offered.

Being fair

Things I suspected and had to drop

Each of these looked like a fault until I tested it with a control. Recording them so nobody chases them again.

  • Hold music. I expected silence, since the stock sound library is missing. Four classical tracks are actually installed and the hold-music setting resolves correctly. Callers on hold hear music.
  • Two API addresses. The switch talks to api.mycountrymobile.com while the portal talks to api2. They return byte-identical responses — same system, two names. Not a bug.
  • Agent status capitalisation. "On Break" and "On break" both exist in the data. The code lowercases before comparing, so it does not matter.
  • Queue agent service missing. The queue script calls a service on a port I did not initially see listening. It is running and answering correctly.
  • The API surface. 314 of 321 portal endpoints exist and are protected. The API is in better shape than the switch.
  • The deployed portal build. Clean — it points at the right API and socket addresses, with no QA leftovers.
  • Referential integrity. No orphaned users, numbers, sites or plans. No duplicate extensions inside a company.

The team has also been notably honest in the product itself: twenty-five "Coming soon" notices across seventeen screens — mostly under Company settings and Roles — each saying plainly that a setting is saved but not yet acted on. That is the right instinct, and it is why the faults above stand out: they are the ones where the screen makes a promise nothing keeps.
