The shape, in one paragraph

There are three layers, and they were built by different people at different times with different rules. The application layer is a large gateway service with fourteen small services behind it, all Node and TypeScript, all in Git. The call-control layer is Kamailio and FreeSWITCH with eight helper services in Python, Lua and Go — this layer lived outside version control until yesterday. The data layer is one central MySQL, twenty-three per-customer MySQL databases, a MongoDB with fifty-five collections, two Redis instances and a message bus that half the platform ignores.

It works. The problems are not exotic — they are the ordinary consequences of the three layers never having been designed together.

Good news: this layer is now under version control, and it matches

I diffed every committed switch file against the live server. 82 of 85 are byte-identical. The three differences are the three files where a secret was deliberately redacted before committing. That is a genuine improvement — a week ago none of this existed in any repository.

Five files on the server are still outside Git: cdr-ingest-v3.py, cdr-ingest-v4.py, two backfill scripts and a trunk test script. The v3 and v4 drafts matter — someone was mid-rewrite of the CDR ingest and stopped. Only v1 is what actually runs.

Two real data problems

1. The tenant databases have drifted apart. Fifteen customers have 12 tables; eight have 14. The two extras are company_settings and company_settings_history — added on 3 September. So the per-section company settings feature works for eight customers and silently does not exist for fifteen.

The cause is structural, not a slip. The tenant migration runner is only ever called when a database is created. Nothing applies a new migration to the databases that already exist. There is one hand-wired exception in the tenant service where a single earlier migration is require()d directly from a controller — that is the workaround, and it does not scale.

2. Backup tables left in production. sites_callerid_backup_20260828, users_role_backup_20260828 and did_countries_package_cost_backup are sitting in the live schema. Harmless today, confusing in six months.

5 · What we have — the honest strengths

  • The service split is sensible. Chat, video, contacts, calendar, SMS, campaigns, CRM as separate services is the right decomposition for this product. It is not a big ball of mud.
  • Every internal service authenticates. Thirteen of fourteen have a purpose-built auth middleware.
  • Internal ports are not reachable from the internet. I tested 3000, 3001, 3004, 3008, 3022, 4222 and 6389 from outside — all blocked by the firewall.
  • Multi-tenancy is real. A per-customer database is genuine isolation, not a company_id column and hope.
  • We own our own campaign-registry account and call the registry directly. Most platforms rent someone else's.
  • Central database migrations exist and are ordered — the discipline is there for the shared schema, just not for tenants.
  • The switch layer is now in Git and byte-matches production.
  • Standard, well-chosen infrastructure: Kamailio for SIP edge, FreeSWITCH for media, coturn for NAT traversal, LiveKit for video, managed MySQL and MongoDB.

6 · What we don't have

G1 · No automated tests. Four files, across 288,823 lines.

One each in asr-manager, campaign-api, chat-api, esl-manager. Nothing in default-api, which is a third of the codebase and handles every payment. There is no CI gate, so a rebuild is a leap of faith — which is exactly why the security patches keep getting wiped by rebuilds.

G2 · No billing, rating or usage service exists at all

Look at the service list again. There is a service for chat, for calendars, for video — and nothing that meters usage, applies a rate, or posts to a ledger. Rating is scattered: a Go service does carrier rates for the SIP proxy, the call records carry a cost column, the billing tables live inside the monolith, and no component joins them. That absence is the architectural root of the billing findings in the previous report.

G3 · Two parallel implementations, one dead, one in production

The systemd unit called fs-xml-api does not run the fs-xml-api repository. It runs a Python rewrite at /opt/fs-xml-api-1.2.5/dialplan_service.py. Same for fs-directory-manager: the Go repo is 1,361 lines and the thing running is a 237-line Python script.

So we are carrying Go repositories in Bitbucket that nobody runs — fs-xml-api (6,874 lines), fs-directory-manager (1,361), fs-callcenter (7,544), directory-manager (1,361), sip-user-data-api, asr-manager (3,789). Roughly 20,000 lines of dead code that a new developer will read and believe.

Either delete them or mark them superseded in their README. Right now the repository lies about what runs.

G4 · The most important process on the platform is single-threaded

The call router is one Python HTTPServer with a small connection backlog and a single database connection. Every call decision — inbound, outbound, transfers, queues, menus — passes through it, one at a time. It has no repository history before yesterday, no tests, and no second instance.

Nothing has fallen over yet because the call volume is tiny. This is the component that will fail first under real load, and when it fails, every call fails.

G5 · Tenant migrations only run at creation

Covered above. The fix is a job that walks every tenant database and applies unapplied migrations — with a per-tenant record of what has been applied. Half a day, and it removes a whole class of "works for some customers" bugs.

G6 · A message bus that half the platform ignores

NATS is installed and running. campaign-api and chat-api genuinely use it. default-api has a full NatsController that subscribes to main.> — and its startup call is commented out.

So the platform has two ways of talking to itself: direct internal HTTP for most things, and a bus for a couple of features. Pick one. Today, the bus is a dependency that is running, costing memory, and doing a fraction of its job.

G7 · esl-manager's authentication fails open

esl-manager is the service that originates outbound calls. Its auth check reads: if no token is configured, allow everyone. On production, no token is configured — there is no environment file at its working directory and its unit sets no environment at all.

Only the firewall stops this being serious, and only two of its routes are guarded anyway. This is the same class of bug as the captcha default that was fixed on 3 September: a missing setting should fail closed, not open.

G8 · The gateway is a third of the backend

default-api is 97,491 lines, 763 endpoints, 44 controllers, 54 models, and it is also the only thing exposed to the internet and also where the billing crons run. Every restart takes down the whole API. It has restarted 97 times on the main box.

This is not something to fix by rewriting. But the next big thing that goes in — usage and rating, for instance — should be a service, not another 5,000 lines here.

G9 · Defence is a single firewall rule

Every internal service binds 0.0.0.0, not 127.0.0.1. They are safe because ufw blocks those ports. One firewall mistake and fourteen services are on the public internet at once. Binding to localhost costs one line per service and removes the single point of failure.

G10 · Smaller gaps worth a line each

  • No API documentation. One swagger file for one of fifteen services.
  • No shared library. Auth, logging and validation are re-implemented in each service, slightly differently — which is why one of them fails open and the others do not.
  • No health checks or metrics. Nothing exports a status. "Is it up" is answered by pm2 list.
  • Two Redis instances with no documented split.
  • An address-verification table with zero rows. The schema for verifying a number's service address exists and has never been written to.
  • Five CDR-ingest versions on disk, four of them dead, plus five dated backups of the running one. That is what editing directly on the server looks like six weeks later.
  • Two machines run the same code against the same database, including the nightly billing job — covered in the billing report.

8 · What to do, in order

  1. Make a missing setting fail closed. Fix esl-manager's auth default, and grep every service for the same pattern. Half a day, and it is the highest ratio of risk removed to effort spent on this page.
  2. Bind internal services to localhost. One line each. Stops the firewall being the only thing between fourteen services and the internet.
  3. Write the tenant migration sweeper — walk every tenant database, apply what is missing, record what was applied. Then run it and give the fifteen customers their settings tables.
  4. Delete or clearly mark the dead Go repositories, and commit or delete the five orphan scripts. A repository that lies about what runs costs every future developer a day.
  5. Put the dist patches into the build. Every one of them is a security or feature fix that a rebuild silently removes. Either merge them into source properly or make the deploy script run the patch scripts.
  6. Add tests where money moves — the payment controller, the renewal cron, the rating helper. Not a coverage target; five tests on the paths that charge cards.
  7. Build usage and rating as its own service, not as more of default-api. This is the same project as the metering work in the billing report — do it once, and put it in the right place.
  8. Decide on the message bus. Either turn default-api's subscriber back on and commit to it, or remove NATS. Half-adopted infrastructure is worse than either choice.
  9. Give the call router a second instance and a health check. It is the single point of failure for every call on the platform.

Method: process and port lists, systemd units, firewall rules and external port tests taken from the live machines; schema and row counts read from the production databases; line counts and structure from the Bitbucket working copies; switch-side files compared file-by-file against the running server by hash.
