Put pricing back into the call ingester

Since 29 August every call is written with cost = 0.000, charge = 0.000. The job that loads calls has no pricing step in it — 392 lines, and the words cost, rate and charge do not appear. Last five days: 108 answered calls, 103 charged nothing.

The good news

The rate data is complete and correct — 92,622 call rates and 651 SMS rates. Only the lookup is missing. And you already have a working model to copy: text messages and faxes both read the balance, refuse when it is short, and deduct. Voice is the only unmetered service.

The change — in /opt/cdr-ingest.py

  1. After a row is parsed and before it is inserted, look the rate up by longest matching prefix: 
    SELECT rate, billingblock, progressiveblock
FROM mycountrymobile_db.call_rates
WHERE service='CALL' AND status='A'
  AND %s LIKE CONCAT(dialprefix, '%%')
ORDER BY CHAR_LENGTH(dialprefix) DESC
LIMIT 1
  2. Bill in blocks, not raw seconds — billingblock is the first block, progressiveblock the increment (default 60). Write the result into cost and charge.
  3. Deduct from companies.credits in the same transaction as the insert, so a crash cannot charge twice. The insert is already idempotent on xml_cdr_uuid — keep it that way.
  4. Increment companies.call_duration_used. It is read in three places and written in none, so plan minute allowances currently do nothing.

Then back-fill

Re-rate everything since 29 August. The rows exist and carry billsec and destination_number; only the price is missing. Do it as a separate one-off script so the nightly job stays simple.

Make IVR menus actually play

"Press 1 for sales" has never run once — zero IVR executions in the switch's entire log. Two separate causes, both about files the switch cannot reach.

Cause 1 — greetings are downloaded where the switch cannot see them

The configuration service downloads a customer's greeting to /var/lib/freeswitch/sounds/<company>/. It runs on the host. FreeSWITCH runs in a container that mounts only /etc/freeswitch and /opt/call-recordings. So the file is written somewhere the switch cannot open. Proof: that host directory exists and is empty, and inside the container the path does not exist at all.

# fs-configuration-api
# internal/freeswitch/xmlcurl/configuration/common/httpapi.go:19
-  freeSwitchSoundsPath = "/var/lib/freeswitch/sounds"
+  freeSwitchSoundsPath = "/etc/freeswitch/sounds/ivr"
# then rebuild and restart fs-configuration-api

That path is already mounted and already holds the customer greetings under /etc/freeswitch/sounds/mcm/greetings/<company>/, so the switch can read it today.

13

Stop the queue script overwriting the ring strategy

Whatever an admin chooses, every queue rings randomly. The lookup service is correct — it returns the queue's real strategy. The queue script sends its own value first, and its own value defaults to random because nothing sets it.

Proof, before you change anything

curl -s "http://localhost:9006/api/callcenter/queues/6124@1785223442786.mycountrymobile.com/agents"
→ "strategy":"ring-all", "rings_together":true   ← what the admin chose

curl -s "http://localhost:9006/api/callcenter/queues/6124@.../agents?strategy=random"
→ "strategy":"random",  "rings_together":false  ← what actually happens

The change — in the dialplan, not the Lua

The cleanest place is the QUEUE branch of dialplan_service.py, which already reads the queue record for its greetings. Set the variable the Lua is looking for:

# in the QUEUE branch, beside cc_queue_name and cc_queue_exten
{"application": "set", "data": f"cc_ring_strategy={queue_ring_strategy(route_value)}"},

Read it from the same place the lookup service does — settings.ring_strategy.value on the queue record.

Do not just change the Lua default from "random" to "". Later branches compare ring_strategy == "ring-all" to decide whether to ring everyone at once, so an empty value silently changes behaviour again. And normalize_strategy is declared at line 390, after get_available_agents at line 237 — so it is not in scope inside that function and calling it there resolves to nil. Fix it in the dialplan and the Lua needs no change at all.

Add an offline presence state

The change

  1. Add the value to the column: 
    ALTER TABLE users
  MODIFY socket_status
  ENUM('online','offline','holiday','away','busy','dnd')

Make the call-path services handle more than one call at a time

Four services sit between the switch and every call. All four are one-request-at-a-time Python servers with a five-deep waiting queue and a single shared database connection.

The four

127.0.0.1:9000   the call router      LISTEN 0 5
127.0.0.1:9001   the phone directory  LISTEN 0 5
127.0.0.1:9002   switch configuration LISTEN 0 5
127.0.0.1:9006   queue agent lookup   LISTEN 0 5

At a 100 ms database round trip that is roughly ten calls a second, ceiling — and any database stall stops all call routing rather than slowing it.

The change — the same three edits, four times

- server = HTTPServer((host, port), Handler)
+ class Server(ThreadingHTTPServer):
+     daemon_threads = True
+     request_queue_size = 128
+ server = Server((host, port), Handler)

Then replace the single module-level _db_conn with a small connection pool — threads sharing one pymysql connection will corrupt each other's results. Keep autocommit=True; that fix is already in and is load-bearing.

Threading without the pool is worse than what you have now: single-threaded at least serialises access to that one connection. Do both edits together or neither.

Check it worked

ss -lntp | grep -E "900[0-2]|9006"      # backlog should read 128, not 5
# then fire 50 concurrent dialplan lookups and confirm every one returns
# the same XML a single request returns — a control matters here

Give audio a fallback on strict networks

The media relay has TCP relaying switched off, and secure relay is offered on port 5349 only. A customer on a corporate network that blocks the usual audio traffic has no second route — the call connects and stays silent. That is how the stuck calls in #02 start.

The change — in /etc/turnserver.conf

# remove this line
no-tcp-relay

# and offer secure relay on 443 as well as 5349,

Then add the TCP and 443 forms to TURN_URLS in the API environment so the browser is actually offered them.

Check it worked

From a network with UDP blocked, place a call and confirm audio both ways. In the browser's WebRTC internals, the selected candidate pair should show a relay candidate — today the browser never allocates one.

Last thing

The rule that would have prevented half of this

Check the machine that takes the calls, not the repository. The most expensive pattern on this project is work that is genuinely finished, genuinely correct, and genuinely absent from production. The two-factor fix is the clearest case: written, committed, correct, never deployed, and being used to bypass login today. Before closing anything on this list, run the verification against 142.93.121.121 — and always with a control, so a blank result cannot be mistaken for a pass.

Two more habits worth keeping, both of which caught mistakes of mine during this review:

  • A zero is not proof until the same search finds something you know is there. Searching the switch for supervisor features returned zero for all seven — that only became a finding once voicemail returned nine on the same search.
  • Test the thing, not the configuration. I expected callers on hold to hear silence, because the stock sound library is missing. Four tracks are actually installed and hold music works. Seven other suspicions died the same way and are listed in the deep audit rather than hidden.

Nothing in this document has been applied. Items 01, 02, 04, 07, 13 and 28 are small and self-contained enough to do immediately.
