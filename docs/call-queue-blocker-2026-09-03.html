Call queue · end-to-end trace

Why The Queue Cannot Be Tested

I followed a real call through every link of the queue path on the live system. The machinery works. The blocker is that the one queue reachable by phone has nobody able to answer it — and the one queue with somebody available has no phone number.

Traced 3 September 2026 Queue Ucaas Test · ext 9331 · 5 numbers Method live probes, each with a control

The blocker in one sentence

No agent can be available at the moment a call arrives, and the two ways of becoming available both leak back to unavailable — one on every page refresh, the other on every socket drop, with nothing that ever puts an agent back.

Everything upstream of that is fine. A call to +1 256 808 1010 is routed correctly, with the right ring strategy, the right wrap-up time, the admin's own hold audio and recording all present. The queue script is in place. The agent-lookup service answers correctly. It gets all the way to the last step and finds an empty room.

The service says so itself, in plain words: "Nobody can take it right now - 1 on a break, 2 signed out."

Root cause

Why nobody can stay available

There are two things that write an agent's status, and both of them only ever push in one direction — towards unavailable.

The button, which un-presses itself

The only place in the whole product to make yourself available is one card on Call Dashboard → Call Queue. It toggles between Available and On Break, and it works. But the same component registers this:

// call-queue-card/index.tsx
window.addEventListener('beforeunload', makeQueueUnavailableOnReload);
window.addEventListener('pagehide',     makeQueueUnavailableOnReload);
// …which sends status: 'On Break'

So an agent is available only while that exact browser tab stays open on that exact page. Refresh it, navigate to the phone, close the tab, or let the laptop sleep, and they are on a break again. That alone makes a two-person test very hard to co-ordinate.

The socket, which logs people out and never logs them back in

Separately, a background event sets an agent's status from whether their browser session is online:

// campaign-api QueueRepository.ts:739
const agentStatus = request.webOnline
  ? { status: "Available",  state: "Waiting" }
  : { status: "Logged Out", state: "Logged Out" };

The logging-out half demonstrably fires. Extension 1794's browser session went offline at 11:06 on 2 September, and their agent record was set to Logged Out at 11:07 — one minute later.

The logging-back-in half does not. Umar (extension 1000) has webOnline: true on his session right now, last seen 07:22 this morning — and his agent record has read "Logged Out" since 26 August. Nine days online, still logged out.

That is the whole root cause. Availability decays and never recovers on its own, so the queue drifts to empty and stays there.

Two smaller things found on the way

  • Ring tiers have no data at all. There are 37 tier records on the platform and every one of them points at a queue that no longer exists. Not one of the sixteen queues has a single tier. The service copes — it treats everyone as one flat level — but "ring these people first, then these" cannot work for anybody.
  • All sixteen queues are still flagged config_applied: false, so whatever step is meant to confirm a queue has been pushed to the switch has never succeeded for any queue.
Do this

How to get a successful queue test today

You can prove the queue end to end in about twenty minutes with two people and one phone, without fixing anything first — as long as you work around the two leaks rather than through them.

  1. Register the agent's phone first

    Sign the agent into the portal and open the phone, so their softphone registers. Confirm it before going further — an unregistered agent cannot be rung however available they look.

    docker exec mcm-freeswitch fs_cli -x "show registrations" | grep 1785312032037
# the agent's extension_web must appear

  2. Use extension 1000, not 1794 or 3689

    1000 is the only member of Ucaas Test with a phone that has ever registered. Adding a second member is a separate task — get one working first.

  3. Go Available on the Call Dashboard, and then do not touch that tab

    Call Dashboard → Call Queue → the Ucaas Test card → the availability button. Then leave the tab alone. Do not refresh it, do not navigate away, do not close it. Refreshing puts you back on a break.

  4. Confirm the switch agrees, before you dial

    This is the step that saves the afternoon. Ask the lookup service directly — if it still says nobody is available, the call will fail and you will learn nothing from making it.

    curl -s "http://localhost:9006/api/callcenter/queues/6a897c00da433e7e71a94c18/agents"

# you want: "agents":[ { … } ]   — a non-empty list
# if it still says "Nobody can take it right now", stop and fix that first

  5. Call one of the five numbers from a real outside phone

    +1 256 808 1010, +1 256 808 1021, +1 442 212 8589, +1 442 212 8593 or +1 854 429 0173. Use a mobile, not another extension in the system — you want the real inbound path.

  6. Watch the switch while it happens

    The first line tells you the call reached the queue at all; the second tells you what it decided.

    docker exec mcm-freeswitch tail -f /var/log/freeswitch/freeswitch.log \
  | grep -E "CALLCENTER QUEUE HANDLER|QUEUE SETTINGS|Querying fs-callcenter"

Expect one thing to still be wrong. If nobody answers, the caller will get silence rather than a "no agents" message, and the voicemail fallback will record nothing. Both are the missing sound library and the voicemail folder — items 11 and 12 on the fix list. That is a separate fault and should not be read as the queue failing.

Then fix

What to change so it works without a ritual

  1. Make the socket path put agents back

    The single highest-value change. Whatever publishes the agent-status event on disconnect must also publish it on connect. The handler already does the right thing with webOnline: true — it is simply never sent. Until this works, every agent on the platform drifts to logged out and stays there.

    Check: log an agent in, then confirm their agent record flips to Available within seconds — without touching the dashboard button.

  2. Stop the page-unload handler signing agents out

    A refresh should not end a shift. Either drop the beforeunload handler and let the socket path own availability, or make it set availability only when the agent has no other session open. As written, the two mechanisms fight each other.

  3. Put the availability control where an agent actually sits

    Today it exists on one dashboard card. An agent taking queue calls lives on the phone screen. The control belongs in the persistent header or the dialpad, visible and settable from anywhere, the way presence already is.

  4. Point a number at a queue that has a working agent

    For the sake of ongoing testing, not as a fix: put one spare number on a queue whose member is you, on a tenant you control. At the moment the only working agent and the only reachable queue are on different customers.

  5. Fix the tier records, or drop the feature from the screen

    All 37 tier records are orphaned and no queue has any. Ring order cannot work for anybody. Either populate them when a queue is saved, or take the tier controls off the queue screen until they do something.

  6. Work out what config_applied is waiting for

    Sixteen out of sixteen queues say false. That is a step that has never succeeded once, not sixteen unlucky queues.
