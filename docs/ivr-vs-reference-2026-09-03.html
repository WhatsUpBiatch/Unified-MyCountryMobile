IVR · two references · one architecture

IVR Against Both References

How the two reference products build a phone menu, how ours is built, and — link by link on the live switch — why a caller who reaches one of our menus today hears nothing and can press nothing. Then the honest answer to "do we have the source to fix it".

Traced 3 September 2026 Refs 14 Dialpad articles read · Genesys from their public API model Ours 5 screens, 3 services, the live switch and its log

Three independent blockers, and no call has ever reached a menu

Our IVR is a flat, single-level key-to-destination menu — the same object the reference products call an "automated response menu" — with a good editor and good guard rails. Against that older shape of the feature we are roughly at parity. Against what both references now sell — a versioned, publishable flow with logic, variables and speech — we have none of it, and that is the honest size of the gap.

But before any of that matters: the menu we do have cannot run. The greeting cannot be fetched (the media API returns 401 to the switch — a regression from the hardening I reported as fixed), the stock prompts do not exist, and every key press transfers into a dialplan context the call router does not serve. Each was proven on the live system with a control. Zero IVR executions appear in six days of switch log.

And we can fix it. The IVR builder's source is complete and matches the running binary. The one file that has to change for key presses to work is the call router — which exists only on the server, edited again this morning, in no repository.

B1 · regressionThe switch can no longer fetch a greeting — and that is on me

The Go service downloads each menu's audio from the media API before writing the menu, using the unauthenticated direct route. In the first audit I reported that route had been closed to everything except faxes and meeting recordings, and called it fixed. It was fixed for strangers. It also closed it to the switch, which had no login and has never sent one.

Verified against the running API, with a control that shows the guard is doing exactly what it was told:

GET /api/media/direct/<company>/greeting/3de491e2….m4a   →  HTTP 401   ← what the switch asks for
GET /api/media/direct/<company>/fax/x.pdf              →  HTTP 404   ← allowed type, file absent

Two further faults sit behind it, both from the first audit and both still true: the download target is /var/lib/freeswitch/sounds/, which the container cannot see, and the Go binary was built on 27 July with that path compiled in.

Owning this. I recommended the media hardening, confirmed it as done, and did not test the one internal caller that depended on the open route. The queue path avoided the same trap by reading Wasabi directly with the media API's own credentials (queue_media.py fetch_greeting). The IVR path should do the same, or the Go service should send the PRIVATE_CALL_SECRET bearer the other internal callers already use.

B2The stock prompt library was never installed

The generated menu hard-wires two system sounds — the invalid-entry prompt and the goodbye — and the switch's sound directory is empty. Same root cause as voicemail's missing prompts in the deep audit. One tarball, one variable, fixes both.

invalid-sound = ivr/ivr-that_was_an_invalid_entry.wav   → /usr/share/freeswitch/sounds/ is empty
exit-sound    = voicemail/vm-goodbye.wav                → missing

B3Every key press transfers into a context the router does not serve

This is the one nobody would have found from the screen. When a caller presses a key, the menu does not bridge the call itself — it hands it back to the dialplan with transfer <target> XML <context>, and the context names the kind of target: extension, ivr, queue, voicemail, number, department, message, ai.

The call router answers requests only for internal, default and public. Asked the live router what it does with each of the seven, next to a control:

CONTROL  context=internal   dest=1731     →  extension name="user-1731"      works
key → EXTENSION   context=extension  dest=1731     →  result status="not found"
key → IVR         context=ivr        dest=<uuid>   →  result status="not found"
key → VOICEMAIL   context=voicemail  dest=1731     →  result status="not found"
key → NUMBER      context=number     dest=9190…    →  result status="not found"
key → QUEUE       context=queue      dest=9331     →  result status="not found"
key → MESSAGE     context=message    dest=x.mp3    →  result status="not found"
key → DEPARTMENT  context=department dest=9324     →  result status="not found"
# static dialplan on the switch defines only: conference, features, public, xfer

So even with audio fixed, the caller hears the menu, presses 1, and the call ends. Only Hang up works, because it is the one key that does not transfer.

ConsequenceZero executions, thirteen menus waiting

Six days of unrotated switch log: 583 ordinary call bridges, zero entries of the ivr application, zero transfers into any of those contexts. Customers on eight tenants have built thirteen menus between them. One is pointed at by a number; none has ever answered a call.

The answer is: the IVR feature itself, yes — the thing it depends on, no. You can rebuild the menu generator, the API and the portal from source today. You cannot rebuild the call router, which is the file B3 has to be fixed in, because it exists only on one disk and was edited again this morning. Committing those six files is the first thing to do — before the fix, not after — so that the fix has somewhere to live.

In order

What to build, and how far each step gets you

Make the menu we have work — about a week

  1. Commit the server-only files

    The router, the queue Lua, the agent service, the shim, the directory service, the ingesters. A deploy script instead of hand edits. Nothing below is safe to change until this exists.

    ½ day

  2. B1 — let the switch fetch greetings again

    Either send the internal bearer from the Go service and accept it on the direct route, or copy the queue path's approach and read Wasabi directly. Point the download at /etc/freeswitch/sounds/ivr/<company>/, which is mounted. Rebuild the binary — the source is there.

    Check: the greeting file appears under the mounted path after one menu request.

    1 day

  3. B2 — install the sound library

    Same fix as voicemail and the queue's no-agent prompt. One tarball into /etc/freeswitch/sounds, sounds_dir repointed, reloadxml.

    Hours

  4. B3 — teach the router the seven contexts

    In do_POST, accept extension · ivr · queue · voicemail · number · message · department · ai and route each to the branch that already exists for the same target type (extension → the user bridge; ivr → the menu; queue → the queue script; voicemail → the voicemail branch; number → the outbound branch). message and department need the new branches from the fix list.

    Check: the seven probes above return an extension name; the control still returns user-1731; then one real call, press 1, and grep -c "EXECUTE.*ivr(" on the switch log goes above zero for the first time.

    1–2 days

  5. Record what the caller chose

    ivr_digit_pressed is already exported on every key. Carry it into call_history so the activity screen can show "pressed 2 → Sales", which is what both references show.

    ½ day

  6. Refuse to delete a menu a number still points at

    Both references block it. Today the number keeps a dead uuid.

    ½ day

Reach the older reference shape — the automated response menu

  1. No-input prompt, exit prompt, uninterruptible message

    Columns exist for the first two. The third is a Play-then-return-to-menu; the reference makes it DTMF-proof.

    1–2 days

  2. Dial by extension as an explicit choice, and dial by name

    Extension already works implicitly once B3 lands. Name needs a directory lookup by keypad letters.

    2–3 days

  3. Text-to-speech

    The Deepgram endpoint is written and commented out — this is the one gap that may be a regression rather than absence. Uncomment, put a language picker on the menu (the field is already stored), cache the rendered file in the greeting library.

    2 days

  4. Per-line fallback when the menu itself fails

    The reference's safety net: if the flow errors, send to voicemail / a queue / a person. Ours ends the call in silence.

    1 day

  5. Split hours, and read the menu's own hours

    Up to four periods per day; and either honour the hours stored on the menu or remove that tab from the menu editor so it stops promising something nothing reads.

    2 days

Reach the current reference shape — flows. Backend first, in this order

  1. Draft, publish, version, lock

    Do this before the builder grows. Retrofitting versions onto a live editor is the expensive way round. Genesys holds three versions; Dialpad two. One is enough to start: published and draft.

    1 week

  2. A step model: Menu · Play · Collect · Branch · Transfer · Hang up · Go-to

    Dialpad's seven core steps, which map cleanly onto FreeSWITCH primitives (ivr, playback, read, regex, transfer, hangup, execute_extension). Stored as a graph, rendered to dialplan by the same Go service.

    3–4 weeks

  3. Variables, system variables, external API step

    Caller ID, called number, collected digits; a GET/POST mid-call with park/resume. This is what turns a menu into self-service.

    2 weeks

  4. Speech recognition

    Needs a module the switch does not have (mod_unimrcp or a streaming ASR via mod_audio_stream, which currently fails to load). Last, and only if customers ask.

    3+ weeks

Where to draw the line. Both references still sell the flat menu — Dialpad calls it the automated response menu and it is on every plan. Getting ours to run (items 1–6, about a week) and to the older shape (7–11, about two more) gives you a menu a small business will not notice is simpler than theirs. Flows (12–15) are two to three months and are what contact centres buy. That is a product decision, not a technical one.

Things I did not copy, on purpose

  • Twenty-one flow types. Genesys runs chat, email, bots and surveys through the same engine. One type — inbound call — is the right first step.
  • Emergency groups and rrule schedules. Clean, and worth adopting when the schedule model is rebuilt; not before.
  • Their words. Nothing in this document proposes putting "Architect" or "Workflow" into the product.
